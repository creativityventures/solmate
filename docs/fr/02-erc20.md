# Chapitre 2 — ERC20 : transfer, approve et l invariante de solde implicite

`ERC20.sol` implemente `transfer` et `transferFrom` sans jamais verifier explicitement que `to != address(0)` ni que le solde de l'expediteur est suffisant avant de le decrementer : `balanceOf[msg.sender] -= amount` echoue naturellement (revert par depassement) si le solde est insuffisant, grace aux verifications automatiques de Solidity 0.8. Le contrat s'appuie sur cette protection native plutot que de dupliquer une verification `require` redondante, un premier exemple du principe "gas optimized" du depot.

L'incrementation du solde du destinataire, elle, est enveloppee dans un bloc `unchecked` avec un commentaire explicite : "Cannot overflow because the sum of all user balances can't exceed the max uint256 value." C'est une invariante globale du contrat (la somme de tous les soldes ne peut jamais depasser `totalSupply`, elle-meme bornee par `uint256`) qui rend la verification de depassement automatique de Solidity superflue a cet endroit precis — economiser ce calcul est sans risque uniquement parce que cette invariante est garantie ailleurs dans le contrat.

`approve`/`transferFrom` traitent une allocation fixee a `type(uint256).max` comme une approbation illimitee qui n'est jamais decrementee, une convention (dite "infinite approval") aujourd'hui largement partagee par les portefeuilles et interfaces DeFi pour eviter de repayer le cout d'approbation a chaque transaction.
